\title{What Must a Relevance Judge See? Evaluating Jev for Task-Level Tool Selection}

\date{September 2026}

\abstract{
Serving each recurring task with a small tool space instead of the whole registry makes tool-using agents more accurate and cheaper to run. We test whether Jev, the TypeSafe System One model, can decide which tools belong in such a space. Jev scores every tool with an independent probability, in three settings: from the request and the tool descriptions for each request (Jev-A), from the same judgments averaged over a task's earlier requests (Jev-B), and from execution traces that show the tool outputs and the executor's answer (Jev-C). We evaluate the three settings against retrieval, usage and trace-based baselines on TGB, BFCL and GTA with eight, six and seven executors. On TGB, a compositional benchmark where a missing upstream tool breaks the chain, the trace-based space improves on serving all tools for every executor, by 2 to 20 points, while the request-based spaces confuse similar data sources and fall below serving all tools for most executors. On BFCL multi-turn function calling, where every tool stays callable and the space decides which tools keep full documentation, the order reverses: request-based spaces are the best methods, and trace-based spaces stay near full documentation because the executor fails most build conversations. Each setting costs a few cents per benchmark.
}

\section{Introduction}

A tool-using language model is usually served with every tool in its registry \citep{toolformer,gorilla,qin2024toolllm}. For requests that recur within a task, a smaller task-specific space removes distractor tools and shortens every prompt. Building that space means deciding which tools a task needs. Retrieval methods decide from tool descriptions \citep{xiao2024cpack,tool2vec}; trace-based methods decide from what the tools returned and what the model answered \citep{zheng2023judging}.

We ask whether an external relevance model can make this decision. Jev \citep{jevdocs} answers yes/no questions about a shared input with independent probabilities, so one call can score every tool in a registry, and each tool's score stands on its own. It is also cheap (\$0.042 per million input tokens) and fast (about 0.3 seconds per call). We evaluate it on TGB \citep{tgb2026}, BFCL \citep{bfcl} and GTA \citep{gta}, with several executors on each, and find:
\begin{itemize}[leftmargin=*,itemsep=1pt,topsep=2pt]
  \item On TGB, from the request and tool descriptions Jev picks the downstream tools but often misses the upstream data source, which breaks the chain; averaging these judgments over a task repeats the mistake. From execution traces, Jev selects every required tool and improves on serving all tools for all eight executors.
  \item On BFCL, request-based spaces beat every baseline and trace-based spaces do not: the executor fails most build conversations, so its traces show the wrong tools.
  \item On GTA, where the executors solve few requests under any space, differences are one to three requests.
\end{itemize}

\section{Jev as a tool-relevance judge}

\paragraph{Interface.}
One call carries a state (a JSON object) and a set of yes/no questions; Jev answers each with an independent probability. We put one question per tool in the state, so a tool's score does not compete with the others. The model version was \texttt{jev-1.13.0}. Prompts are in Appendix~\ref{app:prompts}.

\paragraph{Three settings.}
\begin{itemize}[leftmargin=*,itemsep=1pt,topsep=2pt]
  \item \textbf{\JA{}, per request.} Jev reads an evaluation request and the tool descriptions and is asked whether each tool is needed, including tools whose output feeds another tool. The top $K$ tools serve that request.
  \item \textbf{\JB{}, per task.} The same question on the task's build requests; each tool's scores are averaged, and the top $K$ form a fixed space for the task.
  \item \textbf{\JC{}, per task from traces.} Jev reads a build request, the tool outputs the executor saw under the full registry, and the executor's answer, and is asked whether the answer relies on each tool's output. Scores are averaged and the top $K$ kept as in \JB{}.
\end{itemize}
\JA{} and \JB{} read no executor output, so their scores are shared across executors and only $K$ changes; \JC{} reads each executor's own traces. On every benchmark, all methods of an executor keep the same number of tools per task, fixed in advance from build accuracy, and are evaluated in one session on the same requests. The budget is the same for the baselines and for Jev.

\paragraph{Baselines.}
\emph{Keep all} serves the whole registry. \emph{Random} draws $K$ tools. \emph{BM25}, \emph{Dense} \citep{xiao2024cpack} and \emph{Tool2Vec} \citep{tool2vec} rank tools by lexical or embedding similarity between the tool descriptions and the task's build requests. \emph{Usage Frequency} ranks tools by how often the executor called them in the build traces. \emph{LLM as router} asks the executor itself to name the tools a request needs. \emph{Trace judge} asks the executor which tools support its own answer on each build trace \citep{zheng2023judging}. \emph{TTO} and \emph{Beam Search} are labeled searches over tool subsets on the build requests.

\section{TGB}

\paragraph{Setup.}
TGB has 4,000 text-only requests in ten families of 400 \citep{tgb2026}. Each request is built from a hidden scene (a table, sensor series, calendar, or document corpus) that only the tools can read. Eight families need a chain of two or three tools; \task{compute_only} and \task{no_tool} are controls. The registry has 15 tools: seven chain tools and eight distractors. Every served tool runs once per request, the chain passes outputs downstream, and the executor sees one line \tool{<Tool>: <output>} per served tool. In each family the first 80 requests build spaces and the remaining 320 are evaluated (3,200 in total). Tools are described by the first line of their docstring, as in the baselines; \tool{ExchangeRate} and \tool{Barcode} have no docstring and appear by name. Eight executors are evaluated, each with its own budget per family (2.8 to 6.8 tools on average).

\paragraph{Results.}
Table~\ref{tab:tgb} gives one column per executor. \JC{} improves on Keep all for all eight executors, by 2.5 (Gemma4-12B) to 19.9 points (Qwen3-8B), and is the best reduced space for three executors; it is within one point of the Trace judge for three others, 1.7 points below it on Qwen3-8B and 4.0 below on Qwen3.5-9B. \JA{} and \JB{} fall below Keep all for five of the eight executors and stay 4 to 33 points below \JC{} on every executor. Dense, Tool2Vec and Random stay far below Keep all at these budgets. The following analysis uses Qwen2.5-7B (Figure~\ref{fig:family}).

\JA{} gives the required tools an average score of 0.77 and the other tools 0.12, and it always selects \tool{Calculator}, the last step of most chains. Its mistakes fall on the first step. In three families it replaces the data source with a similar retrieval tool (Figure~\ref{fig:sources}): in \task{fx_settle}, \tool{GoogleSearch} (0.58) replaces \tool{ExchangeRate} (0.39), which has no description; in \task{table_total}, \tool{DocRetrieve} (0.64) replaces \tool{TableQuery} (0.61); in \task{doc_two_facts}, \tool{TableQuery} (0.70) replaces \tool{DocRetrieve} (0.69). Without its source the chain cannot compute the answer, and accuracy in these families drops to 0.3\%, 22.5\% and 28.4\%. Jev gives nearly the same score to a tool on every request of a family, so averaging over the build requests turns these near ties into a fixed wrong choice for the whole family: \JB{} keeps the wrong source in \task{table_total} and \task{doc_two_facts}, and both fall to 0\%.

\begin{figure}[t]

With the tool outputs and the answer in view, Jev scores the required tools at 0.78 on average and every other tool at 0.02, and upstream sources score as high as downstream steps. \JC{} contains the complete chain in every family and recovers \task{doc_two_facts} (99.4\%), \task{fx_settle} (62.8\%) and \task{table_total} (84.1\%). Its remaining errors come from the extra tools that fill the budget in families with a large $K$: Jev gives every non-required tool about the same low score, so the order among distractors carries little information.

\section{BFCL}

We use the 200 records of BFCL v4 \texttt{multi\_turn\_base} \citep{bfcl}, grouped by primary API class (GorillaFileSystem, TradingBot, TravelAPI, VehicleControlAPI), with the first 10 records of each class for building and the other 40 for testing (160 in total). A record's menu holds the functions of its API classes, padded to 30 with functions of other classes. A record succeeds only if the calls across all its turns reach the reference end state, so every tool stays callable: a space is the set of $K$ tools that keep their full documentation, and the other tools keep their signature and one sentence. $K$ is fixed per class and executor from build accuracy. \JA{} reads a test record's user turns; \JB{} averages the same scores over the 10 build records of a class; \JC{} reads the executor's build conversations under full documentation (user turns, calls, tool outputs, replies) and is asked whether the assistant relied on each tool it called. A tool that is missing from a build record's menu, or that the executor did not call, counts as 0 in the class average. Each method is run three times per executor.

\input{tabs/bfcl}

Table~\ref{tab:bfcl} gives the results. On Qwen2.5-7B, \JB{} and \JA{} are the two best methods, 5 to 6 points above full documentation and 2.5 to 3.5 points above the best baselines (Tool2Vec 13.8\%, the router 13.5\%); their lowest runs are above the highest run of every baseline. They also cut the executor's input by more than half (80k and 90k input tokens per record against 208k). \JC{} stays near full documentation. The trace-based space is weak here because the traces are: the executor solves 20\% of the build records under full documentation, and its conversations are dominated by failed and repeated calls, such as switching to \tool{cp} after a failed \tool{mv} when the user asked to move a file. Jev reads these conversations faithfully, so the tools it credits are the ones the executor used, including the wrong ones, and tools the executor never called receive no credit. On TGB, where tool outputs are deterministic and the executor answers most build requests, the same reading recovers every required tool. Averaging over a class does not hurt on BFCL, because records within a class ask for different subsets of the class's functions and the class average ranks the commonly needed functions first.

\section{GTA}

GTA \citep{gta} serves image-based requests with a ReAct agent and an executable tool server. We use two exactly scoreable task types, \task{read_arith} (32 test requests) and \task{count_arith} (15), each split in half into build and test requests. The candidates are the seven tools whose outputs are available (OCR, ImageDescription, Calculator, CountGivenObject, RegionAttributeDescription, TextToBbox, Solver); every space keeps two tools. Jev reads the request text and the tool descriptions (\JA{}, \JB{}) or the executor's full-menu build trajectories (\JC{}); the images themselves are not shown.

\input{tabs/gta}

Table~\ref{tab:gta} gives the results. The executors answer few GTA requests under any menu, so the methods differ by one to three requests. On Qwen2.5-7B, the three Jev spaces tie with TTO and Beam Search at 4 of 32 \task{read_arith} requests, above every other method, and on \task{count_arith} \JA{} solves 3 of 15, where the best baseline solves 2 and Keep all 1. \JC{} has little to read here: the 7B executor calls a tool in 6 of 33 \task{read_arith} and 2 of 15 \task{count_arith} build trajectories, so most tools never appear in a trace.

\section{Cost}

Jev input costs \$0.042 per million tokens and output is free. \JA{} adds one call per request, about 1,800 input tokens, 0.3 seconds and \$0.00008 on TGB. \JB{} and \JC{} are built once: 800 calls and \$0.06 to \$0.07 for all ten TGB families, 80 calls and \$0.01 for BFCL, and about \$0.01 for GTA per executor. \JA{} and \JB{} scores are shared across executors.

% ---------------------------------------------------------------------
\section{Conclusion}

What an external relevance judge should read depends on the quality of the traces. On TGB, tool outputs are reliable and the executor answers most build requests, so the execution trace is the input that matters: from requests Jev confuses similar data sources, and from traces it selects every required tool and improves on serving all tools for every executor. On BFCL, the executor fails most build conversations, so its traces point to the wrong tools, and spaces built from the requests are the ones that help. Next steps are larger registries and deciding from the traces themselves when they are good enough to use.

\section{Prompts}
\label{app:prompts}

\paragraph{\JA{} and \JB{}.} Input: the request and the 15 tool descriptions. One question per tool \texttt{T}:
\begin{quote}\small\ttfamily
For the user request `request`, would an agent need to call the tool T (described in `tools`) to answer it correctly? Count a tool as needed if its output is required at any step, including intermediate steps whose result feeds another tool. Judge only from the request and the tool descriptions.
\end{quote}

\paragraph{\JC{}.} Input: the request, the tool outputs the executor saw, and the executor's answer. One question per tool \texttt{T}:
\begin{quote}\small\ttfamily
An assistant answered the request `request` after seeing the outputs in `tool\_outputs` and gave the final answer `answer`. Does that answer rely on the output of the tool T? Say yes if the answer uses information that appears in that tool's output, directly or through another tool's output that was computed from it. Do not judge whether the answer is correct and do not answer the request yourself.
\end{quote}
